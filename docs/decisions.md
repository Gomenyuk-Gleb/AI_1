# Decisions log

## Data
- Source: `albertvillanova/legal_contracts` on HuggingFace (SEC EDGAR commercial
  contract filings, same domain/era as CUAD v1, which the full ContractLens
  project uses downstream). Chosen over downloading the full CUAD v1 archive
  (hundreds of MB of PDFs on Zenodo) because step 1-2 only need 30 raw contract
  texts, not CUAD's clause annotations yet.
- 30 contracts spanning 10 types (employment, lease, loan/credit, consulting,
  shareholder/standstill, stock option, amendment, termination, supply/
  manufacturing, indemnity/control agreements) — see `data/contracts_manifest.json`.
- Long contracts (>4400 words) truncated head+tail (first ~3200 + last ~1200
  words) rather than naive head-only truncation, so governing-law/termination/
  signature clauses (usually near the end) survive alongside the opening
  recitals (parties/dates). This is a lighter stand-in for the full project's
  planned map-reduce extraction.
- 10 golden docs hand-labeled by reading the full text (`data/golden/ground_truth.json`),
  deliberately including edge cases: a blank day-of-month date, a no-single-date
  letter agreement signed on three different dates, an agreement with no
  governing-law clause at all, and two docs that don't cleanly fit the agreement_type
  enum (tests the `other` bucket).

## Schema (`src/contractlens/schema.py`)
8 fields: `agreement_type` (enum), `parties` (nested list of `Party{name, role}`,
`role` itself an enum), `effective_date`, `governing_law`, `term_description`,
`has_termination_clause`, `has_confidentiality_clause`, `key_obligations` (list[str]).
Exceeds the assignment's minimum (6 fields, 1 enum, 1 nested object/list).

## LLM gateway (`src/contractlens/llm.py`)
- `litellm` as the single interface to both cloud (`CLOUD_MODEL`, LiteLLM format,
  e.g. `gemini/gemini-flash-latest`) and local (`LOCAL_MODEL=ollama/llama3.2:3b`)
  models, so swapping providers is a one-line `.env` change.
- `instructor.from_litellm(...)` for schema-validated structured output with
  automatic re-prompting (the model gets the Pydantic validation error back and
  retries) — this *is* the "JSON невалідний -> retry з текстом помилки" behavior
  from the assignment, not hand-rolled, because instructor already implements it
  correctly.
- Two retry layers: an outer `tenacity` retry (network/timeout/rate-limit errors,
  exponential backoff, 3 attempts) around an inner instructor validation retry
  (`MAX_RETRIES`, default 3). `REQUEST_TIMEOUT_S` (default 30s) bounds every call.
- **instructor mode matters a lot for small local models**: the default `TOOLS`
  mode (OpenAI-style function calling) made `llama3.2:3b` hallucinate unrelated
  content instead of calling the tool at all. Switching to `instructor.Mode.JSON`
  for any `ollama/*` model (schema is embedded in the prompt + `format=json` on
  the Ollama side) fixed this completely. Cloud models keep `TOOLS` mode, which
  is the more reliable path for frontier APIs.
- `num_ctx=8192` is passed explicitly for Ollama calls — Ollama's default context
  window is much smaller than the model's max, and with the default our ~4-6k
  token contract prompts were silently truncated, which was the root cause of
  the early hallucinated responses (see above).
- Cost ledger: every call (success or failure) is appended to
  `data/results/llm_calls.jsonl`; `COST_LIMIT_USD` is enforced as a hard stop
  *before* each cloud call by summing that ledger, mirroring the full project's
  planned `COST_LIMIT_USD` / HTTP 402 behavior in miniature.

## Evaluation (`eval/evaluate.py`)
- `agreement_type`: exact match. `parties`: set-F1 with fuzzy name matching
  (rapidfuzz ratio ≥ 75). `effective_date`: exact match after normalization
  (both-null counts as a match). `governing_law` / `term_description`: fuzzy
  ratio ≥ 75 (free text). `has_termination_clause` / `has_confidentiality_clause`:
  exact boolean match. `key_obligations` is reported but not scored (open-ended
  free text, not reliably gradable without an LLM judge — left for stage 2).
- `overall_field_accuracy` = unweighted mean of the per-field means above.
- Cost/1000 docs = mean per-doc cost over the run × 1000 (not a separate
  pricing table), since LiteLLM already returns real per-call cost via
  `completion_cost()`.

## Measured results (local model, `ollama/llama3.2:3b`)

Full numbers: `eval/reports/stage1_2.md` (generated by `eval/evaluate.py`).

| config | docs | valid JSON | overall field acc | p50 latency | p95 latency | $/1000 docs |
|---|---|---|---|---|---|---|
| a_deterministic (temp=0, top_p=1) | 30 (all) | 76.7% | 0.457 | 18.7s | 45.8s | $0 |
| b_creative (temp=0.7, top_p=0.9) | 10 (golden) | 40.0% | 0.423 | 27.9s | 42.5s | $0 |

Per-field accuracy (config a, graded against the 10 golden docs — 8/10 parsed validly):
`agreement_type` 0.75, `parties` F1 0.95, `effective_date` 0.375, `governing_law`
**0.0**, `term_description` 0.125, `has_termination_clause` 0.75,
`has_confidentiality_clause` 0.25.

Takeaways:
- **Temperature hurts structured-output reliability more than it helps content
  quality** for this 3B model: `b_creative` is both less often valid JSON (40%
  vs 77%) and slightly *less* accurate on the fields it does get out, while
  being slower (higher latency — longer, more rambling completions).
- The model is reliably good at `parties` and reasonable at `agreement_type`,
  but essentially never extracts `governing_law` correctly — either omitting
  it (safe) or occasionally hallucinating a US state from a party's state of
  incorporation rather than an actual governing-law clause (seen in ad hoc
  testing, not the final run). It under-reports rather than over-reports most
  other free-text fields, i.e. it tends to say "not stated" instead of
  inventing content, which is the safer failure mode for a legal-document tool.
  `has_confidentiality_clause` is weak (0.25) because the model frequently
  misses confidentiality clauses that are present but not spelled out as
  their own labeled section.
- At `temperature=0`, failures are **deterministically repeated**: e.g. on
  `contract_017` the model confidently outputs `agreement_type:
  "clinical_manufacture_and_supply"` (not a valid enum value) on every one of
  4 retry attempts, because deterministic sampling reproduces the same mistake
  even after instructor feeds back the exact Pydantic validation error. A
  model-side fix would need either a slightly higher temperature *specifically
  on the retry turn*, or a few-shot example of the enum in the prompt; this is
  left as a stage-2 follow-up, not fixed here, since the current behavior is
  itself useful evidence for "qwen/llama-class local models are not
  production-ready for this schema without prompt iteration."
- Instructor's default `TOOLS` mode (OpenAI-style function calling) was
  unusable for this model — it never emitted a tool call and instead
  hallucinated unrelated content; `MD_JSON` mode was necessary (see above).

## Known limitations (step 1-2 scope)
- Cloud leg requires an API key in `.env`; no key was available in this
  environment, so only the local model (`ollama/llama3.2:3b`, already pulled)
  was actually run end-to-end. The code path is identical for both — running
  `--model cloud` after adding a key produces directly comparable numbers.
- `llama3.2:3b` was used instead of the `qwen3:4b` mentioned in the parent
  project doc, since it was already pulled locally; both are small
  tool-calling-capable Ollama models in the same size class.
